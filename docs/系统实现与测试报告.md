### 1.2 项目架构概述

SukinOS 是一个运行在浏览器端的**桌面操作系统 Web 应用**，采用前后端分离架构：

- **前端（本仓根目录，源码在 `src/`）**：React 19 + Redux Toolkit，模拟桌面操作系统核心体验——窗口化多任务、应用动态加载、虚拟文件系统、进程间通信及安全沙箱隔离。数据完全存储在用户浏览器本地（IndexedDB）。
- **后端（本仓子目录 `myfastapi_/`）**：FastAPI + SQLAlchemy + Celery + Redis，提供用户认证管理、SukinOS 应用商店、请求日志审计、WebSocket 实时通信、SSE 本地开发热重载等服务。

##### (2) JWT 双 Token 认证系统 (Api/Common/Auth.py)

系统实现了完整的 **Access Token + Refresh Token** 双 Token 机制：

```python:19:55:myfastapi_/Api/Common/Auth.py
def create_access_token(data: dict, remember: bool = True):
    """创建短期 Access Token (用于业务请求)"""
    to_encode = data.copy()
    expires_delta = timedelta(seconds=ACCESS_TOKEN_EXPIRE_MINUTES)
    expire = datetime.now(timezone.utc) + expires_delta
    to_encode.update({
        "exp": int(expire.timestamp()),
        "type": "access",
        "remember": remember
    })
    encoded_jwt = jwt.encode(to_encode, SECRET_KEY, algorithm=ALGORITHM)
    return encoded_jwt, int(expires_delta.total_seconds())

def create_refresh_token(data: dict, remember: bool = True):
    """创建长期 Refresh Token (仅用于刷新 Access Token)"""
    to_encode = data.copy()
    expires_delta = timedelta(seconds=LONG_REFRESH_TOKEN_EXPIRE)
    expire = datetime.now(timezone.utc) + expires_delta
    to_encode.update({
        "exp": int(expire.timestamp()),
        "type": "refresh",
        "remember": remember
    })
    encoded_jwt = jwt.encode(to_encode, SECRET_KEY, algorithm=ALGORITHM)
    return encoded_jwt, int(expires_delta.total_seconds())
```

**认证特性**：
- Access Token：30分钟有效期，用于业务请求
- Refresh Token：7天有效期，用于静默刷新
- 支持"记住我"模式（Cookie max_age 控制）
- 密码使用 bcrypt 哈希存储
- 三级权限模型：角色模式 (role)、位运算权限 (power)、超级管理员 (superuser)

`verify_auth()` 工厂函数实现了**四阶段认证流程**：
1. **第一阶段**：校验 Access Token
2. **第二阶段**：Access Token 无效时，自动用 Refresh Token 静默刷新（生成新 Token 对并注入 Response Cookie）
3. **第三阶段**：基础用户状态校验（is_active 检查）
4. **第四阶段**：详细权限校验（角色/位运算）

##### (8) 应用多版本与审核迭代 (Func/system/appVersionService.py + appVersionPolicy.py)

应用包从"单行覆盖"改为**当前版本单行 + 历史版本独立表**：

- **当前可用版本**只存在 `sukinos_app` 一行；所有非当前版本（含待审暂存）落在 `sukinos_app_revision`。
- **待审优先**：开发者的新版本一律先写入 `sukinos_app_revision` 并标记 `is_pending`，审核通过后才替换当前行；审核期间线上版本保持可用。
- **单待审约束**：同一资源同一时间只允许一个待审版本。开发者重复提交只替换自己来源的待审包；其他情况返回 409，审核端需显式 `replaceExisting`。
- **服务端发号**：版本号由 `next_business_version()` 在当前行与全部历史（含已删除）中取最大版本、末段 +1，20 字符上限；非数字末段返回 400，不静默回退。包内旧版本号会被重写。
- **状态机**：`sukinosAppPolicy` 统一维护 `under_review / active / disabled` 的合法迁移；审批与回滚只换版本，已下架应用保持下架（`promotion_target_status`）。
- **修订保留**：系统配置 `sukinos_app_revision_retention`（`maxRevisions`，1–200，默认 20）在每次重提后剪枝；当前包本体始终保留。
- **系统包只读**：`is_reserved_system_resource()` 拦截 `sys-*` 保留资源的改包与强更，必须走内部发布签名通道。

管理端版本接口：`GET /system/sukinos/versions/{id}`、`POST .../approve|reject|activate|delete|restore|meta`；开发者侧 `POST /sukinos/app/update` 在存在任意历史修订时拒绝原地更新，必须先提交待审版本。

##### (9) 包完整性校验、强制更新与客户端联动

- **服务端哈希与签名**（`Func/system/appPackageTrust.py`）：落盘后计算 worker 包体 SHA-256；对 `f"{resourceId}\n{version}\n{contentHash}"` 做 Ed25519 签名，十六进制入库。环境变量 `SUKIN_APP_SIGN_PRIVATE_KEY`（32 字节 base64 种子，兼容 urlsafe）、`SUKIN_APP_SIGN_KEY_ID`、`SUKIN_APP_SIGN_REQUIRED`；开启必签时签名失败直接 500，不放行未签名包。
- **客户端校验**（`src/sukinos/utils/process/packageTrust.js`）：安装/更新时重算 SHA-256 并用 `VITE_APP_SIGN_PUBLIC_KEY` / `VITE_APP_SIGN_KEY_ID` 验证 Ed25519 签名；历史迁移包没有哈希时降级为告警放行，0 字节包直接拒绝。
- **更新投影**：`checkUpdates` 只对本人应用、公开应用或注册池已授权应用返回；投影含 `contentHash / signature / signKeyId / signAlg / forced`。回滚到更低版本时 `force_update=1`，客户端即使本地版本更高也接受这次"降级更新"。
- **内核轮询**（`kernelParts/updates.js`）：30 分钟自动检查，页面重新可见且距上次检查超过 5 分钟时补检；强更清单写入 `localStorage` 键 `sukinos:forced-updates`（`forceUpdateGuard.js`）。
- **冷启动拦截**（`kernelParts/lifecycle.js`）：非系统应用若命中强更且本地版本不一致，拒绝启动并发出 `APP_FORCE_UPDATE`；普通可更新应用发 `APP_UPDATE_AVAILABLE`。DeskBook 负责排队确认弹窗，商店通过 `storeSearch` token 深链定位到应用。
- **管理端开关**：`POST /system/sukinos/forceUpdate`（root）只允许对已上架应用开启，开启前调用 `verify_current_package()` 确认当前包可用。

##### (10) 文件服务与静态分发收紧 (Func/system/appFileService.py + sukinosAppPolicy.py)

##### (4) 虚拟文件系统 VFS (src/sukinos/utils/file/fileKernel.js)

基于 IndexedDB 的类 Unix 文件系统：

```javascript:5:49:src/sukinos/utils/file/fileKernel.js
class fileKernel {
  constructor() {
    this.driver = new fileIndexDb()
    this.inodeMap = new Map()   // 内存镜像: id -> Inode
    this.treeMap = new Map()    // 目录树索引: parentId -> Set<childId>
    this.events = new EventTarget()
    this.ready = false
  }
  async boot() {
    await this.driver.mount()
    const inodes = await this.driver.loadAllInodes()
    this.inodeMap.clear()
    this.treeMap.clear()
    if (inodes.length === 0) {
      await this.#formatDisk()
    } else {
      inodes.forEach(node => this.#syncMemory(node))
      if (!this.inodeMap.has(ROOT_INODE_ID)) await this.#formatDisk()  // 根节点丢失时重建
    }
    this.ready = true
    return true
  }
  #syncMemory(inode) {
    this.inodeMap.set(inode.id, inode)
    if (inode.parentId) {
      if (!this.treeMap.has(inode.parentId))
        this.treeMap.set(inode.parentId, new Set())
      this.treeMap.get(inode.parentId).add(inode.id)
    }
  }
}
```

`ready` 是关键门控：`boot()` 一次性把整库读成 `inodeMap` + `treeMap` 两份内存结构，之后的 `readdir`/`readFile` **同步查内存**，IndexedDB 只在挂载和写入时参与。所以 VFS 的性能形态是"启动全量读 + 运行期写穿透"，而不是"每次 IO 走 IDB"。（副作用：多个标签页各持一份镜像，跨标签写同一用户库时可能发散。）

提供多层次安全防护：

- **SDK 冻结**：防止运行时篡改

关于 `Function` 的口径要写准：**不是全面禁用，而是按 `envType` 放行**。逻辑沙箱（`envType: 'worker'`）拿到的是真构造器，因为把预编译的逻辑模块包成 factory 需要它；UI 沙箱仍返回 `_forbidden` 占位对象，调用即抛 `Security Error: Function is not allowed in sandbox.`（`security.js:getSharedSandboxUtilities`）。另有 `set` 陷阱侧的 `blockedProps` 清单（`security.js:blockedProps`，含 `fetch`/`eval`/`Function`/`window`/`document`/`self`/`globalThis`/`navigator` 等），拦的是"重新赋值这些属性"，与上面的 `get` 分支是两套东西。这条 `envType` 差异是"主逻辑块 import 到 UI 侧仍能执行"的前提，也是 UI 侧不硬拒逻辑 import 的依据。

```sql
    status        VARCHAR(20),                -- 快照时状态，不参与可用性判断
    audit_opinion VARCHAR(255),
    is_private    BOOLEAN NOT NULL DEFAULT FALSE,  -- 可见性快照，回滚时一并恢复
    is_pending    BOOLEAN NOT NULL DEFAULT FALSE,  -- 待审暂存；同一资源最多一条
    is_deleted    BOOLEAN NOT NULL DEFAULT FALSE,
    deleted_at    DATETIME,
    deleted_by    INT,
    file_purged   BOOLEAN NOT NULL DEFAULT FALSE,  -- 物理包已清除，不可恢复
    source        VARCHAR(20) NOT NULL DEFAULT 'developer',
    operator_id   INT,
    diff_note     VARCHAR(500),               -- 改包文件名与行数增减摘要
    content_hash  VARCHAR(64),
    signature     VARCHAR(128),
    sign_key_id   VARCHAR(32),
    created_at    DATETIME DEFAULT NOW(),
    INDEX idx_revision_resource (resource_id)
);
```

同一资源同一时间只允许一条 `is_pending=1 AND is_deleted=0` 的记录；审批通过时当前行快照写入本表，
待审行内容替换当前行。修订保留由 `sukinos_app_revision_retention` 控制，剪枝只清理最旧的超额修订
及其无引用物理包。

### 2.4 新增版本/安全链路的验证方式

多版本审核、包哈希/签名、强制更新、文件治理与隔离预览这批改动**没有新增 pytest 用例**（`tests/` 仍为
5 个文件、66 个 `def test_`），交付侧采用以下验证：

| 验证项 | 方式 |
|--------|------|
| 语法/静态检查 | `npx eslint` 覆盖改动文件；`npx esbuild --loader:.jsx=jsx --jsx=automatic` 逐个转译 9 个改动 JSX；CSS Modules 用 postcss 解析 |
| 版本号与状态机 | `appVersionPolicy` 的纯函数（`compare_versions` / `next_business_version` / `pending_decision` / `promotion_target_status` / `can_purge`）可脱离数据库直接断言 |
| 包完整性 | 服务端 `sign_package()` 与客户端 `verifyRemotePackage()` 共用同一 manifest（`resourceId\nversion\ncontentHash`），用固定密钥对做对称验证 |
| 强制更新 | 内核 `Updates` 30 分钟轮询 + 冷启动 `lifecycle` 拦截 + `forceUpdateGuard` 本地缓存，按"写入-读取-清理"三步手工回归 |
| 隔离预览 | 需浏览器实机验证 opaque-origin iframe、CSP 拦截、20s ready 超时与 4 次加载上限；headless 环境无法完整复现 |
| 数据库变更 | 按 `docs/sql/` 直接执行 SQL（库名 `sukin`），不使用 Alembic；本报告不记录线上执行结果 |

> 结论口径：静态检查通过 ≠ 功能验收。版本审批、签名校验与预览沙箱的最终验收仍需在可连数据库、
> 可运行浏览器的环境中按上表逐项复测。
